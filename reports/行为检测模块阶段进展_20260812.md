# 行为检测模块阶段进展

更新时间：2026年8月12日

## 一、当前结论

行为检测模块的初版原型架构已经可以确定，采用“实时骨架检测 + 疑似事件多模态复核”的两阶段方案：

```text
摄像头视频流
  ↓
统一视频接入与帧缓存
  ↓
人体检测/跟踪 + 姿态关键点提取
  ↓
ST-GCN++ 时序动作识别
  ↓
NORMAL / SUSPECTED / CONFIRMED / COOLDOWN 状态机
  ├─ 正常：继续实时检测
  └─ 疑似跌倒：截取事件前后 2～4 秒 RGB 视频
                    ↓
              Qwen3-VL / V-JEPA 复核
                    ↓
       告警等级、动作类别、原因解释、事件摘要
                    ↓
             FastAPI 接口输出至系统
```

该架构兼顾实时性和解释能力：骨架模型承担持续、低延迟的安全筛查；多模态模型不逐帧常驻运行，而是在疑似事件触发后读取 RGB 片段进行语义复核，避免大模型阻塞实时检测。

## 二、已经完成的工作

### 1. 骨架检测与时序分类路线

- 已完成 RTMPose、YOLO-Pose、ByteTrack、RTMO、OpenPose、AlphaPose、Hourglass 等前端与 ST-GCN++、CTR-GCN、PoseC3D-style 分类头的组合对比。
- 共实测 23 条路线，采用 GMDCSA24 四名受试者隔离四折测试；每条路线每折训练 300 轮，总训练量为 27,600 epochs。
- 当前内部测试最高路线为 `YOLO-Pose + ByteTrack + ST-GCN++`，Balanced Accuracy 为 89.41%，跌倒召回率为 92.41%。
- 综合内部结果和 MCFD 跨数据集测试，当前较稳健的单路线为 `RTMPose + ST-GCN++`：内部 Balanced Accuracy 为 86.83%，特异度为 90.12%。
- ByteTrack 能提高人物连续跟踪和部分路线的跌倒召回率，但在跨数据集场景中没有稳定增益，因此保留为候选开关，不直接作为最终默认配置。

### 2. 多模态模型调研与实跑

#### V-JEPA 2.1

- 已实际接入 V-JEPA 2.1-B，直接读取 RGB 视频并提取 768 维视频语义特征。
- 完成 160 段视频特征提取和 300 轮分类头/融合头训练。
- V-JEPA 单路在整段均匀采样时 Balanced Accuracy 为 70.71%；由骨架模型先定位疑似窗口后提升至 80.01%。
- `RTMPose + ST-GCN++ + V-JEPA` 后融合内部 Balanced Accuracy 为 87.51%，略高于骨架单路的 86.83%，但不同受试者上的增益不稳定，暂作为疑似事件复核分支，不替换实时主线。

#### Qwen3-VL

- 已完成 Qwen3-VL-2B 对视频片段的零样本二分类、五分类和结构化输出实验。
- 五分类初步覆盖站立/行走、坐姿、躺卧、弯腰/下蹲、跌倒等姿态与动作状态；在平衡 50 段小样本试验中准确率为 76%。该结果用于工程初筛，不能与完整主体隔离测试直接等价比较。
- 在 MCFD 192 段平衡外部测试中，专用 FALL/SAFE 零样本提示的 Balanced Accuracy 为 72.92%、特异度为 98.96%，适合承担高置信语义确认，但跌倒召回率只有 46.88%，不适合单独承担安全主链路。

#### Qwen3-VL + QLoRA

- 已使用 GMDCSA24 的 123 段训练视频进行 QLoRA 微调，更新约 321 万个 LoRA 参数，完成 3 轮训练。
- 验证集最佳 Macro-F1 为 86.45%，Balanced Accuracy 为 87.50%。
- QLoRA 将结构化回答解析错误降为 0，但 MCFD 外部测试 Balanced Accuracy 为 69.27%，低于专用零样本提示的 72.92%，说明目前主要提升了输出格式稳定性，尚未提升跨数据集泛化能力。
- 当前二分类标签不足以监督可靠的动作阶段和原因解释；后续如继续微调，需要补充经人工核验的多类别、跌倒阶段、方向、倒地后状态和原因标注。

#### 其他候选模型

- InternVideo3、LLM-AR 等已列入后续对照候选，但当前阶段尚未形成与现有数据协议一致、可公平比较的完整实跑结果，因此暂不写入最终性能排名。

### 3. 系统原型与接口

- 已完成视频解码、YOLO-Pose、64 帧骨架窗口、四折 ST-GCN++ 集成推理和告警状态机。
- 已封装 FastAPI 原型，提供启动/停止检测、运行状态、跌倒事件、最新标注帧和 MJPEG 预览等接口。
- 本地视频全链路冒烟测试已跑通：共解码并处理 77 帧，姿态有效率 100%，单次最新推理延迟约 12～16 ms，无断流重连错误。
- 跌倒和日常活动演示视频均已生成；8 段流程冒烟测试中，4 段跌倒均产生确认告警，4 段日常活动均未报警。该测试用于验证系统流程，不作为无偏模型准确率，正式性能以上述主体隔离测试为准。
- 当前代码测试共 18 项，全部通过。

### 4. 萤石摄像头接入

- 摄像头在线，开放平台应用、AccessToken、设备识别和官方 Windows PC SDK 均已连接成功。
- 已完成“保持视频加密，通过 EZOPEN + 官方 PC SDK + 设备验证码取流”的路线 A 接入代码，不需要关闭设备视频加密。
- 2026年8月11日和8月12日进行了两次受控真机测试，均返回错误码 `525546`，表示 VTDU 两路取流并发已满。
- 测试没有抢占、停止其他组员的流，也没有修改摄像头设置；由于尚未取得真实视频帧，目前“摄像头实时画面 → 跌倒检测 → FastAPI 告警”的真机闭环仍待验证。

## 三、目前存在的问题

1. 萤石当前只允许两路 VTDU 并发；如果前端预览、跌倒检测和其他模块分别直接拉流，会再次出现并发占满。
2. 现有公开数据与实际老人居家场景存在视角、遮挡、服装、光照和动作差异，需要补充摄像头现场数据。
3. V-JEPA 和 Qwen 的增益具有样本/受试者差异，尚不能直接取代骨架实时主线。
4. Qwen/QLoRA 当前原因描述受训练模板影响，不能把生成的文字直接视为真实跌倒原因。

## 四、下一步计划

### 1. 完成真机闭环

- 协调释放一路萤石预览会话，进行一次 15～30 秒真机验证。
- 将 SDK 码流回调直接接入实时解码，不再采用“先录制完整视频、再离线处理”的中间方式。
- 验证实时帧率、端到端延迟、断线重连、告警触发和资源释放。

### 2. 建立统一视频接入服务

正式系统采用“一次拉流、多模块共享”，而不是每个模块分别向萤石申请视频流：

```text
萤石摄像头（仅占用一路）
        ↓
统一拉流/解码/帧缓存服务
  ├─ 跌倒检测
  ├─ 心理状态分析
  ├─ 行为与姿态识别
  ├─ 多模态事件复核
  └─ Web 前端预览
```

每个模型使用独立的有界队列；慢模块只丢弃自己的旧帧，不能阻塞视频接入和其他模块。Qwen 等大模型只读取触发事件前后的缓存片段。

### 3. 现场测试与数据迭代

- 采集站立、行走、坐下、躺卧、弯腰、下蹲、快速坐下、遮挡和模拟跌倒等现场片段。
- 统计事件级召回率、误报次数/小时、告警延迟和姿态不可用率。
- 对现场误报进行困难负样本回灌，再决定 RTMPose/YOLO-Pose、ByteTrack 和多模态复核的最终组合。

## 五、当前可交付状态

目前可以交付的是：初版技术架构、23 条骨架路线实验、V-JEPA/Qwen/QLoRA 实跑结果、本地视频检测程序、告警状态机、FastAPI 原型及萤石官方 SDK 接入代码。

尚未完成的是：萤石真机实时视频帧闭环、统一视频共享服务、现场数据测试及与师兄业务系统的最终联调。
